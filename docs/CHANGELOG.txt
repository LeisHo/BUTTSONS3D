2026-09-04 -- 03:44 AM (single timestamp; session start not separately measured)

Fixed the screen-space OutlinePass outline toggle (`outlineUsePostprocessing`)
being invisible, and updated the Rhino-exported BUTTON MODEL source files to
the user's latest export.

Fixed:
- OutlinePass composites its edge color with THREE.AdditiveBlending by
  default. This project's outline color defaults to black (#000000), and
  additive blending with black adds (0,0,0) to the scene -- a no-op. The
  pass was rendering every frame, just invisibly, for exactly the color
  everyone was testing with. Root-caused by live-debugging in the browser:
  setting visibleEdgeColor to cyan made the outline immediately visible,
  confirming the pass itself worked and the color was the issue. Fix: set
  `pass.overlayMaterial.blending = THREE.NormalBlending` on both
  `outlinePassBase` and `outlinePassCap` (index.html) so the edge alpha-
  blends over the scene instead of adding to it, which composites correctly
  for any edge color including black.

Updated:
- `data/BUTTON MODEL.fbx` (+ `.fbxbak`) replaced with the user's latest
  Rhino export. Verified via live FBXLoader inspection in the browser: all
  4 named parts (BUTTON_BASE, BUTTON_EXTERIOR, BUTTON_INTERIOR_-_UNPRESSED,
  BUTTON_INTERIOR_-_PRESSED) are present with bounding boxes identical to
  the prior version, so no code changes were needed. Also answered a
  standing question from the user: Rhino's FBX export does not preserve the
  Active/Archived master-layer structure from the source .3dm -- only
  flat object-level names survive in the export -- so duplicate "Active"
  sublayer names under different master layers are not a source of
  ambiguity for this pipeline, and Archived-layer geometry is confirmed
  absent from the exported file.

Verified:
- Live in the Browser pane, both before and after the fix: toggled the
  "Outline: Use Screen-Space Pass" checkbox on a clean page reload and
  screenshotted the result. Before the fix, the outline was essentially

2026-09-04 -- 05:03 AM - 05:10 AM EDT

Fixed OutlinePass drawing occluded outlines through foreground buttons,
reported directly with a screenshot: "outlines seem to render fully on
top of everything... The outline of a button being obscured by another
button in front, should not have its entire outline shown. only for
areas where the button is visible."

Fixed:
- OutlinePass's own edgeDetectionMaterial gives a "hidden" (occluded)
  edge pixel the same alpha as a genuinely visible one -- they only
  differ by color (hiddenEdgeColor vs visibleEdgeColor). Under the
  AdditiveBlending this pass used before an earlier fix, that was
  harmless as long as hiddenEdgeColor was black (adding zero draws
  nothing) -- which is exactly why a black VISIBLE edge was ALSO
  invisible, the bug the earlier NormalBlending fix addressed. But
  NormalBlending has no such free cancellation, so occluded edges
  started drawing just as opaquely as visible ones. Patched
  edgeDetectionMaterial's fragment shader (inspected live, not guessed)
  so a hidden edge's alpha is forced to 0 -- contributes nothing under
  any blending mode, true depth-respecting occlusion. Applied via
  runtime string-replace against the exact pinned three@0.169.0 shader
  source, with a console.error guard if the match ever fails on a
  future version bump.

Verified:
- Live in the Browser pane: screenshotted before/after with the
  screen-space outline enabled -- before, outlines traced full circles
  around every button top and cut through occluding neighbors in
  criss-cross patterns; after, outlines only trace the actual visible
  silhouette, correctly stopping where another button occludes. A real
  click still functions with the pass enabled. Checked console on 2
  genuinely fresh tabs (not the long-lived test tab, whose console
  history persists across reloads and showed a stale shader-patch-
  failure error from an earlier whitespace-mismatch attempt) -- zero
  errors on either fresh tab.

Fixed:
- Discovered (via `AskUserQuestion` ruling out a stale local-save theory
  for the zoom issue, then fetching the deployed site's actual HTML and
  reproducing live at a mobile viewport) that the outline bug was real
  and reproducible on a completely clean load -- just only at
  devicePixelRatio 2+ (real phones), not the devicePixelRatio 1 desktop
  environment used for all of today's earlier testing.
- Root cause confirmed directly against EffectComposer.js's own source:
  its constructor caches renderer.getPixelRatio() once, and every pass's
  setSize() reuses that cached value forever -- never re-reading the
  renderer's live pixel ratio. This project constructs the composer
  before resize() ever runs (resize() is what raises the renderer's
  pixel ratio to match the device, up to 2x); on desktop that cached "1"
  happens to already be correct, which is exactly why extensive desktop
  testing never caught this. On a real high-DPI phone it left the 2
  OutlinePass instances' own internal render targets sized for 1x while
  the main canvas actually draws at 2x -- a genuine resolution mismatch.
- Fixed by calling composer.setPixelRatio(renderer.getPixelRatio()) in
  resize() -- a real method the class already exposes.

Verified:
- Reproduced the exact bug (funnel-shaped gaps, no button outline) at a
  devicePixelRatio:2 mobile viewport on a clean load, both against the
  live deployed site directly and locally via resize_window mobile
  emulation, before writing any fix.
- After the fix: clean outlines at devicePixelRatio:2, confirmed desktop
  (devicePixelRatio:1) stays visually unchanged (correctly a no-op
  there), and a real click still functions with no console errors.
