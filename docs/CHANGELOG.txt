2026-09-04 -- 03:44 AM (single timestamp; session start not separately measured)

Fixed the screen-space OutlinePass outline toggle (`outlineUsePostprocessing`)
being invisible, and updated the Rhino-exported BUTTON MODEL source files to
the user's latest export.

Fixed:
- OutlinePass composites its edge color with THREE.AdditiveBlending by
  default. This project's outline color defaults to black (#000000), and
  additive blending with black adds (0,0,0) to the scene -- a no-op. The
  pass was rendering every frame, just invisibly, for exactly the color
  everyone was testing with. Root-caused by live-debugging in the browser:
  setting visibleEdgeColor to cyan made the outline immediately visible,
  confirming the pass itself worked and the color was the issue. Fix: set
  `pass.overlayMaterial.blending = THREE.NormalBlending` on both
  `outlinePassBase` and `outlinePassCap` (index.html) so the edge alpha-
  blends over the scene instead of adding to it, which composites correctly
  for any edge color including black.

Updated:
- `data/BUTTON MODEL.fbx` (+ `.fbxbak`) replaced with the user's latest
  Rhino export. Verified via live FBXLoader inspection in the browser: all
  4 named parts (BUTTON_BASE, BUTTON_EXTERIOR, BUTTON_INTERIOR_-_UNPRESSED,
  BUTTON_INTERIOR_-_PRESSED) are present with bounding boxes identical to
  the prior version, so no code changes were needed. Also answered a
  standing question from the user: Rhino's FBX export does not preserve the
  Active/Archived master-layer structure from the source .3dm -- only
  flat object-level names survive in the export -- so duplicate "Active"
  sublayer names under different master layers are not a source of
  ambiguity for this pipeline, and Archived-layer geometry is confirmed
  absent from the exported file.

Verified:
- Live in the Browser pane, both before and after the fix: toggled the
  "Outline: Use Screen-Space Pass" checkbox on a clean page reload and
  screenshotted the result. Before the fix, the outline was essentially
  invisible against the grid; after, it renders as a bold black silhouette
  matching the existing geometry (inverted-hull) outline's appearance.
  Confirmed the checkbox's off state (geometry outline) is unaffected.
  Checked the browser console for errors after reload -- none. Timing was
  not captured via start/finish shell timestamps this turn (task picked up
  mid-session after a context-compaction resume) -- logged as
  Actual: NOT MEASURED in ETA History accordingly.

2026-09-04 -- 04:17 AM - 04:42 AM EDT

3-item round: user asked to port OKCILCOKCID's camera architecture, then 2
more reports arrived mid-turn while that was in progress ("click and drag
to reorder function doesnt work well. the dragged element becoms dark",
"outlien doesnt work well. Its making an outline for ALL BUTTONS and ALL
BASES etc... AND the outline doesnt work in black. looks like a blending
issue").

Added:
- Camera architecture ported from OKCILCOKCID: position sliders (X/Y/Z)
  now translate camera.position AND controls.target together (true
  world-space translation, doesn't swing the view angle -- the same
  "you provided me rotation sliders only" bug that project's own history
  already fixed once). Added Camera Yaw/Pitch sliders (rotate target
  around a fixed position/distance -- a genuine "turn in place",
  independent of position/zoom) and a Camera Zoom slider (distance-to-
  target). Camera panel values now sync from live state every frame
  (previously only on Copy/Save Settings clicks), so mouse-driven
  orbit/pan/zoom shows up in the sliders immediately. Camera presets now
  store position+FOV+Zoom only (no target), matching the reference
  project's exclusion of target from a preset's identity. Removed
  cameraTargetX/Y/Z; bumped SETTINGS_SCHEMA_VERSION to 3.

Fixed:
- Drag-to-reorder rows/groups reading as "becoming dark" while dragging:
  root cause was `opacity:0.4` on the dragged item, which against this
  panel's near-black background made the text nearly disappear instead
  of clearly indicating what's being moved. Swapped for full opacity
  plus a light background tint and an accent-colored outline.
- OutlinePass (screen-space outline) merging neighboring buttons into
  one connected outline: it draws an edge only where its own selection's
  mask touches an UNselected pixel, so it can't tell two different
  SELECTED objects apart -- with one shared selectedObjects array per
  mesh-type across the whole grid, any two orthogonally-adjacent
  same-type cells whose silhouettes touched on screen merged into one
  outline (visible as long wavy lines running down entire rows). Split
  each mesh-type into a checkerboard 2-coloring by grid cell
  ((row+col)%2) -- 4 OutlinePass instances instead of 2 -- so no two
  orthogonally-adjacent cells ever share a selection. Not a full
  per-object fix (that needs one pass per cell, infeasible for a grid
  this size); a diagonal touch between same-color cells could still
  merge, a rarer case than the row-wise merging this specifically fixes.
- Caught and fixed a self-introduced bug while porting the camera
  architecture, via direct live camera/target inspection rather than
  visual inspection alone: an initial draft kept a redundant wholesale
  position re-apply after the per-slider replay loop in
  applyAllSettings(), which silently clobbered the Camera Zoom slider's
  own already-correct replay on Reset/boot. Removed the now-dead
  applyCameraSettings() wholesale function entirely.

Verified:
- Camera: live-tested position-translate (Yaw/Pitch/Zoom stayed exactly
  constant while translating), Yaw-rotate (position/Zoom stayed exactly
  constant while rotating), Zoom (direction stayed constant), Reset (via
  window.__debug live inspection -- confirmed position/target/zoom end
  up mutually consistent, not just visually plausible), and Save/Use
  Camera preset round-trip (exact value match). Confirmed a fresh reload
  renders identically to before the port (no regression to the default
  view).
- Drag-dark fix: reproduced the exact pre-fix visual (opacity 0.4,
  computed style confirmed) via real PointerEvent dispatch on the grip
  element, then confirmed post-fix computed style (opacity 1, tinted
  background, accent outline) and that the class is correctly removed on
  drop.
- Outline merging fix: screenshotted before (long connected wavy lines
  across rows) and after (each button visibly separated) with a real
  reload between; confirmed a real click still functions with the
  screen-space pass enabled; checked the console after each change (only
  pre-existing transient local-dev-server ERR_CONNECTION_RESET entries
  from rapid reloads, no new script errors).

2026-09-04 -- 05:03 AM - 05:10 AM EDT

Fixed OutlinePass drawing occluded outlines through foreground buttons,
reported directly with a screenshot: "outlines seem to render fully on
top of everything... The outline of a button being obscured by another
button in front, should not have its entire outline shown. only for
areas where the button is visible."

Fixed:
- OutlinePass's own edgeDetectionMaterial gives a "hidden" (occluded)
  edge pixel the same alpha as a genuinely visible one -- they only
  differ by color (hiddenEdgeColor vs visibleEdgeColor). Under the
  AdditiveBlending this pass used before an earlier fix, that was
  harmless as long as hiddenEdgeColor was black (adding zero draws
  nothing) -- which is exactly why a black VISIBLE edge was ALSO
  invisible, the bug the earlier NormalBlending fix addressed. But
  NormalBlending has no such free cancellation, so occluded edges
  started drawing just as opaquely as visible ones. Patched
  edgeDetectionMaterial's fragment shader (inspected live, not guessed)
  so a hidden edge's alpha is forced to 0 -- contributes nothing under
  any blending mode, true depth-respecting occlusion. Applied via
  runtime string-replace against the exact pinned three@0.169.0 shader
  source, with a console.error guard if the match ever fails on a
  future version bump.

Verified:
- Live in the Browser pane: screenshotted before/after with the
  screen-space outline enabled -- before, outlines traced full circles
  around every button top and cut through occluding neighbors in
  criss-cross patterns; after, outlines only trace the actual visible
  silhouette, correctly stopping where another button occludes. A real
  click still functions with the pass enabled. Checked console on 2
  genuinely fresh tabs (not the long-lived test tab, whose console
  history persists across reloads and showed a stale shader-patch-
  failure error from an earlier whitespace-mismatch attempt) -- zero
  errors on either fresh tab.

2026-09-04 -- 07:49 AM - 07:56 AM EDT

User pasted a Copy Settings dump ("set defaults") plus 3 requests: an
OutlinePass-specific thickness slider, "weird outline overlap still
occurs with black outlines," and the key diagnostic clue -- "when i
change the outline color, the outline does change, but the black lines
overlapping surfaces dont."

Added:
- "Outline Thickness (Screen-Space Pass)" slider (outlinePassThickness,
  0-4px, maps to OutlinePass.edgeThickness) -- separate from the
  existing Outline Thickness slider, which only puffs the geometry
  (inverted-hull) outline meshes outward in local space and has no
  meaning for the screen-space pass. Relabeled the existing one
  "(Geometry)" to disambiguate.
- Set defaults from the pasted dump (camera position/Yaw/Pitch/Zoom/FOV,
  outline thickness/color/outlineUsePostprocessing now ON by default,
  1 saved camera preset, panel geometry/collapsed-group state) -- no
  git-tracked settings log exists yet for this project, so the pasted
  values became the new defaults directly per CLAUDE.md 12m.

Diagnosed (the important finding):
- Reproduced the user's exact scene (their pasted settings, including
  the narrow 10-degree FOV and far zoom) and found the "black lines
  overlapping surfaces" the user described -- dark seam marks at the
  base-to-cap gap between neighboring buttons. Tested decisively by
  turning outlineEnabled OFF entirely: the dark seams were STILL
  present, proving they are NOT an outline-system artifact at all --
  they're the extension cylinder's own toon-shaded shadow side
  (toonShadowFloor is 0% in the user's settings, i.e. true black
  shadows), made visible in the gaps at this specific steep/narrow-FOV
  camera angle. This directly explains the user's own diagnostic clue:
  changing outlineColor recolors the actual outline (pink, correctly)
  but has no effect on these dark seams because they were never outline
  pixels to begin with.
- Reported this finding to the user with the controlled-experiment
  screenshot (outline off, dark seams still there) rather than
  continuing to treat it as an outline bug.

Verified:
- New thickness slider tested at both extremes (0 and 4) -- visibly
  changes screen-space outline glow/thickness, no console errors.
- Set-defaults values verified against a cleared localStorage (so stale
  saved state from earlier in-session testing couldn't mask whether the
  new DEFAULT_SETTINGS values actually took effect).
